# Архитектура

## Главный принцип — четыре зоны не смешиваются

1. **Устанавливаемый универсальный продукт** — этот репозиторий: навыки, онтология,
   контракты, скрипты, шаблоны, синтетические тесты. Без данных конкретных людей.
2. **Отдельно лицензируемый методический модуль** — Negociar-RU, русская адаптация Negociar
   (CC BY-NC-SA 4.0, оригинал © Artur Galiev). Встроен в плагин, но физически отделён папками
   `skills/negociar-ru/`, `translation-negociar-ru/`, `licenses/negociar-ru/` с собственными
   лицензией, NOTICE и provenance.
3. **Приватные профили и накопленные данные пользователя** — `profile/`, `negotiations/`,
   `knowledge/` в его папке или проекте. Никогда не входят в продукт.
4. **Внешние провайдеры и их учётные данные** — PLAUD, WonderScribe, локальная
   транскрипция; ключи только в переменных окружения; аккаунты в поставку не входят.

## Источники истины

1. `negotiations/` — материалы и подтверждённый разбор каждой встречи;
2. `knowledge/` — актуальное накопительное состояние;
3. `profile/` — роль, организация, политики пользователя;
4. `review.yaml` — решения и подтверждения пользователя по встрече;
5. `core/ontology/` и `core/contracts/` — допустимые сущности, поля, значения.

`system/` — только пересоздаваемый слой (контрольный центр, очередь, поиск). Он не заменяет
канонические источники и не хранится в проекте claude.ai.

## Поток

```
источник → шлюз согласия → SourcePacket (sha256, сегменты, спикеры)
  → review.yaml (карта спикеров, границы) → 11 JSON по контрактам (лёгкий профиль — 01/07/08) → validate (схема + строгая проверка цитат)
  → report_auto.md → report.md (факты / интерпретации / подтверждения) → follow-up (draft_not_sent)
  → knowledge_proposal.json (+ учёт: у каждого объекта разбора одна судьба) → knowledge_diff.md
  → ответы по сомнительным пунктам (knowledge_decisions.jsonl) → новый diff → подтверждение → knowledge apply
  → ledger.jsonl (append-only) → refresh-all (очередь, проекция, поиск, контрольный центр)
  → брифинг следующей встречи
```

## Хранилище в трёх режимах

Одна и та же раскладка путей; отличается только носитель:

- **папка** (Claude Code, Cowork) — скрипты работают напрямую;
- **проект claude.ai** — канонические файлы являются документами проекта с теми же путями;
  локальная рабочая копия `na-workspace/` на время разговора; встреча хранится как
  `analysis_bundle.json` + `report.md` + `review.yaml` + `meta.yaml` (+ транскрипт, если
  шлюз разрешил хранение);
- **только разговор** — без накопления, результаты в тексте.

Правила выбора и синхронизации — `skills/negotiation-system/references/store-adapter.md`.

## Доставка по хостам — что работает где

Плагин один, а хосты дают ему разные возможности. Поэтому агенты и хук — ускорители и
страховка поверх навыков, а не единственный механизм: каждое правило, которое держит хук,
записано в навыке, и у каждого шага, который делает агент, есть текстовый путь.

| Хост | Навыки | Скрипты `na.py` | Агенты | Хук защиты базы |
|---|---|---|---|---|
| Claude Code | да | да; путь к плагину подставляется только в текст навыков и агентов, в Bash переменная пуста | да | да |
| Cowork | да | да; в облачном режиме — над копией папки в сессии (по внешним замерам) | по внешним замерам — да | только если хук видит папку: в облачном режиме не видит (по внешним замерам) |
| Проект claude.ai | да | нет — текстовый путь | нет | нет |
| Codex (по внешним замерам, не проверено нами) | да, из `.claude-plugin/plugin.json` | если есть оболочка; переменные в тексте навыка не подставляются | нет | хуки типа command — после доверия пользователя; пути из `apply_patch` хук разбирает, на живом Codex не проверено |

Подробности для пользователя — `docs/INSTALL.md`, раздел «Что работает где».

**Хук.** Решает по входу вызова и по признакам рабочей папки на диске (`.na-workspace`,
`knowledge/workspace.json`, `system/workspace.json`, `knowledge/events/ledger.jsonl` или пара
`knowledge/` + `negotiations/`). Нет признаков, не разобран вход, нет `python3` — пропускает: хук не
должен мешать посторонней работе. Цели записи ищет во всех путях записи, которые видит хост:
инструменты правки, команды оболочки (эвристический разбор: перенаправления, `tee`, `sed -i`,
`cp`/`mv`/`rm`, `python -c` и heredoc, командлеты PowerShell) и заплатка `apply_patch`. Вызов `na.py`
— законный путь записи в базу; его собственная запись не проверяется. Разбор команды — эвристика:
запись через переменную, вычисляемый путь или отдельный скрипт не видна, это страховка поверх
правил навыка. В рабочей копии режима проекта (`na-workspace/`) разрешено только создавать файлы —
так документы проекта загружаются в копию.

**Ответ владельца.** Подтверждение пользователя — инвариант, но модель может поставить
`--confirm` сама (например, если другой плагин в сессии требует «решать самому»). Поэтому команды
`na.py`, фиксирующие решение владельца, хук сверяет с последним вводом человека в транскрипте
сессии — репликой или ответом на вопрос с вариантами: нужно явное согласие без отказа, а для
применения и отправки — после показа (diff, предпросмотр). Транскрипт не читается или ответ на
вопрос ещё не записан — хук не судит: отказ без уверенно прочитанной реплики мешал бы владельцу в
хостах, чей формат транскрипта хук не знает, и подталкивал бы модель к обходам; правила навыков
действуют и без хука. Из субагента такие команды не выполняются.

**Агенты.** Получают пути и задание, а не разговор; главный агент держит разговор с
пользователем и читает только JSON — длинный транскрипт не вытесняет контекст. В базу агенты не
пишут: `transcript-analyst` пишет только файлы частей и артефакты встречи, `evidence-verifier`
файлов не пишет вовсе (отчёт сохраняет главный), у `reader` нет ни одного инструмента. Маршрут
обработки, разрешённый шлюзом, не меняется: агенты работают в той же сессии и у того же
провайдера модели.

## Инварианты

1. Сырые источники не изменяются после фиксации границ анализа.
2. Любой поведенческий вывод содержит цитату, таймкод и уверенность.
3. Подтверждение пользователя не выдаётся за фразу из транскрипта.
4. Производное представление можно удалить и полностью пересобрать.
5. Один идентификатор обязательства или риска не может одновременно находиться в активном и закрытом состоянии.
6. Ручные пометки `(m)` не перезаписываются автоматически.
7. Ошибка схемы или ссылка на отсутствующую сущность блокирует статус `ready`; информационный пробел — не блокирует.
8. Открытый вопрос и незавершённый анализ — разные состояния.
9. Аудиометрики не используются как детектор лжи, намерений или манипуляций.
10. Контрольная дата не заменяет исходный срок обязательства.
11. Память меняется только после показанного diff и явного подтверждения.
12. Follow-up и проекты сообщений всегда `draft_not_sent`.

## Приоритет настроек

Безопасность и лицензии → явное решение пользователя по конкретному источнику → политика
организации → ролевой профиль → универсальные значения по умолчанию. Профиль не может
ослабить согласие, доказательность или лицензионные ограничения.

## Два контура распространения

**Универсальный дистрибутив** (этот репозиторий): код, навыки, схемы, пустые шаблоны,
синтетические тесты, документация.

**Приватный рабочий каталог** пользователя: конфигурация, профиль организации, источники,
накопленные знания, журналы, производные. Не публикуется.

## Правило миграции

Архитектурные изменения внедряются добавлением нового слоя рядом с текущим. Массовая
перезапись `knowledge/` допускается только после резервной копии, автоматической сверки
количества и идентификаторов сущностей, сравнения всех пометок `(m)`, проверки на
существующих встречах и явного отчёта о различиях.

Версия схемы рабочей папки хранится в `knowledge/workspace.json` (каноническая, пишет только
движок). Изменения раскладки оформляются нумерованными идемпотентными миграциями
`na.py migrate`: план без записи → явное подтверждение `--confirm` → запись версии и списка
изменённых файлов; реестры и журнал событий миграции не трогают.
