# Движок `scripts/na.py`

Единая точка входа детерминированной части системы. Только стандартная
библиотека Python 3.10+; сетевых вызовов нет, кроме отправки себе в Telegram
(`deliver telegram-link`, `deliver send`); единственный секрет — ключ бота (переменная
`NA_TELEGRAM_BOT_TOKEN`, `delivery/secrets/telegram_bot_token` или
`~/.config/negotiation-analysis/telegram_bot_token`). LLM-этапы (11 аналитических JSON,
финальный `report.md`, `knowledge_proposal.json`) движок не выполняет — он
регистрирует, проверяет, собирает, показывает diff и применяет только после
подтверждения пользователя.

```text
python3 <plugin>/scripts/na.py [--root R] [--json] <команда> [подкоманда] [параметры]
```

- `--root R` — рабочий каталог с данными (workspace). Если не задан, берётся
  переменная окружения `NA_WORKSPACE`, иначе текущий каталог. Флаг допустим как
  до, так и после подкоманды.
- `--json` — печатать результат машинно-читаемым JSON вместо короткой сводки.
- Код плагина и данные разделены: схемы — `<plugin>/core/contracts/`, шаблоны —
  `<plugin>/templates/`, всё остальное — в workspace.

команде, которая в них нуждается.

## Подкоманды

Общие ключи: `--root R`, `--json`, `--version` (версия движка и плагина).

### Источник

`source create --meeting <id> --transcript <file> [--note <file>] [--provider manual|plaud|wonderscribe|local_file|uploaded_transcript|document] [--captured-at ISO] [--title "..."] [--external-id ...] [--allow-duplicate]`

Создаёт `negotiations/<id>/`, копирует транскрипт в `transcript.txt` без
изменений, пишет `source_packet.json` (SourcePacket: `source_id`, `provider`,
`source_type`, `external_id_or_local_path`, `captured_at`, `ingested_at`,
`content_sha256`, `segments` с таймкодами `[HH:MM:SS]`/`HH:MM:SS` и метками
`Speaker N:` / `Имя:`, `speaker_labels`, `sensitivity: unknown`,
`processing_status: registered`, `consent`/`masking_mode`/`allowed_routes`/
`retention_decision: not_set`), а также скелеты `meta.yaml` и `review.yaml`.
В `review.yaml → source_scope` — границы анализа: `analyzed_from`/`analyzed_until` и
исключённый фрагмент `excluded_from`/`excluded_until` (`null` в `excluded_until` — до конца
записи) с `exclusion_reason`. Отдельной команды для них нет: заполняются по подтверждению
пользователя вместе с `01.excluded_source_range` (`from`/`to`/`reason` — та же граница).
Дедупликация: если встреча с таким же `content_sha256` уже есть — отказ (код 2)
с указанием существующего id; `--allow-duplicate` регистрирует с полем
`duplicate_of`.

`source gate --meeting <id> --consent yes|no --masking none|initials|pseudonyms|full --sensitivity public|internal|confidential|regulated --routes local_only|local_and_cloud_llm [--retain-source yes|no]`

Записывает решение шлюза в `review.yaml` (`processing_gate`, `source:
user_confirmation`) и `source_packet.json`. При `consent=yes` статус
`gate_passed`, иначе `blocked_by_gate`; без `yes` конвейер не считает встречу
готовой. Решение относится только к этой записи и не наследуется другими.

### Спикеры и ручная проверка

`speakers set --meeting <id> --map "Speaker 1=Иван Петров (CFO);Speaker 2=..."`

Карта спикеров в `review.yaml` (`speaker_mapping.status: confirmed`, `source:
user_confirmation`) и в `source_packet.json` (`speaker_map`). Роль в скобках
необязательна.

`review confirm --meeting <id> [--status confirmed|confirmed_with_open_items|pending]`
— фиксирует `review_status` (информационное поле).

### Профиль разбора

`profile set --meeting <id> --profile light|full`

Записывает в `review.yaml` решение пользователя `analysis_profile: {mode, source:
user_confirmation, recorded_at}` (короткая форма `analysis_profile: light` тоже
читается; нет ключа — `full`). `full` — все 11 артефактов. `light` («только
обязательства и риски») — обязательны `01_extraction.json`, `07_commitments.json`,
`08_risks.json`: 07 и 08 ссылаются только на участников, организации и темы из
01, а 09–11 — производные от 01–08, поэтому для лёгкого разбора не нужны.
Остальные артефакты — «не выполнялись по профилю», это не ошибка. `validate`,
`report`, `followup`, `manifest`/`status`, `refresh`, `refresh-all` и контрольный
центр учитывают профиль; шлюз, карта спикеров и проверка цитат те же. Файл вне
профиля, если он есть, проверяется валидатором, но в отчёт этого профиля не
входит. Неизвестное значение профиля в `review.yaml` — ошибка `validate`. Переход
`light → full` делает недостающие артефакты снова обязательными (`resume_from:
analysis_complete`).

### Проверка, отчёт, follow-up, манифест

`validate --meeting <id>` — артефакты профиля разбора по
`core/contracts/contracts.schema.json` (встроенный schema_runtime), формат
таймкодов, совпадение `meeting_id`, порядок границ `excluded_source_range` (`to` не раньше
`from`) и строгая проверка каждой цитаты (`quote`, `source_quote`, `related_quote`,
`prior_position_quote`, `reaction_quote`, `evidence_quote`, в том числе во вложенных списках:
`source_quotes`, `evidence`, `related_mentions`) по `transcript.txt` и его сегментам →
`analysis/validation_report.json`. Код 1 при ошибках. Непройденный шлюз и отсутствие
`report.md` — предупреждения.

Проверка цитаты (`scripts/na_engine/quote_check.py`):

| Результат | Что значит | Статус |
|---|---|---|
| `exact` | буквальное вхождение | норма |
| `normalized` | совпадение без учёта регистра, ё/е, видов кавычек и тире, пунктуации, пробелов и переносов | допустимо, помечается |
| `ellipsis` | цитата с «…»/«...»: части по порядку внутри одной реплики или соседних реплик того же говорящего | допустимо, помечается |
| склейка | цитата складывается только через стык реплик разных говорящих | ошибка |
| не найдена | ни одним способом | ошибка `quote not found in transcript` |
| атрибуция | `used_by`/`speaker` (02, 03, 04, 05, 06, 10) ≠ говорящий реплики по карте спикеров; прежняя позиция уступки (05) сверяется с `prior_position_speaker`, если он задан, иначе со `speaker` | ошибка при подтверждённой карте; иначе предупреждение |
| атрибуция обязательства | `who` (07) ≠ говорящий якоря | предупреждение: якорем может быть принятие другой стороной |
| без атрибуции | `related_mentions` (07: предложение, принятие, подтверждение, прежняя версия) и `evidence` участника (01: самопредставление, обращение по имени) | цитата и таймкод проверяются, говорящий — нет |
| таймкод | заявленный таймкод дальше ±15 с от интервала реплики | предупреждение; ошибка, если он — начало другой реплики |

Говорящий реплики: метка сегмента (`Speaker N` или имя, встреченное хотя бы дважды) →
`review.yaml speaker_mapping` → участник `01_extraction`; строка без таймкода и метки
продолжает предыдущую реплику. Одинаковая фраза в нескольких местах сопоставляется с
ближайшей к заявленному таймкоду. В отчёт проверки добавлены `quote_stats` (уровни,
склейки, атрибуция, таймкоды), `source_quality` (сегменты, таймкоды, метки говорящих,
статус карты, несопоставленные метки), `quote_checks` (результат по каждой цитате),
`timestamp_tolerance_sec`, `analysis_profile`, `skipped_by_profile`.

`report --meeting <id>` — `report_auto.md`: первая строка после заголовка —
**Данные:** (провайдер, число реплик, есть ли таймкоды и разметка говорящих, статус
карты спикеров, уровни совпадения цитат, профиль разбора, дата реестров, чего нет),
затем блок «Один экран» (главный вывод,
требуемое решение, ключевые факты, риски, варианты, следующий шаг — из 01/07/08/
09/11; в лёгком профиле — из 01/07/08 с пометкой, что 09/11 не строились) и полные
разделы; в «Контроль качества» — подраздел «Качество источника» (разметка, уровни
цитат, атрибуция, таймкоды, список цитат не дословно, предупреждения). В лёгком
профиле вместо разделов 02–06, 09–11 — раздел «Не выполнялось по профилю».
Правила сборки:

- «Требуемое решение» — все области 09: сначала открытые, затем записанные как
  принятые с пометкой «(записано как принятое)». Принятым считается только решение, чьё
  `current_state` начинается со статусного префикса «Принято», «Решено», «Согласовано» или
  «Утверждено» (без учёта регистра), за которым идёт «:», «.» или «—» («Принято: аванс 20 %»).
  Всё остальное — открытое, без эвристик по тексту: «Не решено: …», «Отложено: …»,
  «Отменено: …», «Договорённости нет: …», «Согласовано только с юристами …», пустое
  состояние, старые артефакты без префикса.
- Срок обязательства без даты — срок словами: «до пятницы (даты нет)»; столбец
  «Кто → кому».
- Человек не из участников 01 (ЛПР, владелец риска, `who`/`to_whom`): если о нём есть
  наблюдение в `09.authority_observations` — первое предложение `observed_role` с
  пометкой «(не участник встречи)», иначе `` `id` (не участник встречи) ``; сырой id
  не печатается. Пометка — только у строк-идентификаторов (`^[a-z0-9][a-z0-9-]*$`,
  например `p-nordtech-ceo`); свободный текст вместо id («не установлен: сторона …»)
  печатается как есть, без пометки.
- Исключённый фрагмент записи — «с `from` до `to`», при `to: null` — «до конца
  записи»; в старых артефактах без `excluded_source_range.to` конец берётся из
  `review.yaml → source_scope.excluded_until`, если он есть.
- Первый экран: факты и риски с confidence `certain`/`probable` (риски — сначала high);
  риск high ниже probable не скрывается, а помечается «требует проверки»; остальные
  риски ниже probable — только в «Рисках: актуальное состояние» (столбец «Уверенность»
  с пометкой) и строкой «ещё N … ниже probable». Обязательство ниже probable на первом
  экране — с пометкой «(требует подтверждения)».
- Карта спикеров «подтверждена пользователем» — только при `status: confirmed` и
  сопоставлении всех меток; если часть меток без `person_name`/`person_id` —
  «подтверждена частично (без сопоставления: …)»; `proposed` — «предложена, не
  подтверждена»; иначе — «не подтверждена».

Проверка полноты — `analysis/report_auto_validation.json` (обязательные заголовки
своего профиля, участники, обязательства и риски встречи). Обязательства
и риски берутся из реестров knowledge/, а ещё не внесённые — из 07/08 с пометкой
«анализ (в базу не внесено)». Код 1, если проверка полноты не пройдена.

`followup --meeting <id>` — `follow_up.json`, `follow_up_protocol.md`,
`follow_up_message.md`; `delivery_status` всегда `draft_not_sent`, отправки нет.
Протокол — внутренний документ: итог, все решения карты, действия, открытые вопросы с
цитатами, риски, очередь проверки, правило следующей встречи. Сообщение — черновик другой
стороне, только:

- принятые решения 09 — только по статусному префиксу `current_state` («Принято»,
  «Решено», «Согласовано», «Утверждено» и «:», «.» или «—» — то же правило, что
  «Требуемое решение» отчёта), confidence не ниже probable; без префикса, «Не решено: …»,
  «Отложено: …» — в сообщение как принятые не попадают; текст после префикса — как есть
  («в договоре не оформлено» не убирается);
- действующие обязательства обеих сторон (статус не `done`/`cancelled`, confidence не
  ниже probable) со сроками;
- открытые вопросы 07 — только формулировка вопроса (до первого «?», без «?» — первое
  предложение), без цитат, таймкодов и id;
- следующий шаг: просьба подтвердить договорённости и сроки.

Итога разбора, открытых решений, рисков, рекомендаций аналитика и очереди проверки
(выводы низкой уверенности, манипуляции) в сообщении нет. Из текста разбора в сообщении
убираются скобки с таймкодом, id или ссылкой на пункт («(C1)»), а известные id встречи
заменяются: человек — подписью, риск и обязательство — ничем.

Сборка — теми же правилами, что `report_auto.md` (хелперы `report.py`):

- Срок обязательства без даты — срок словами: «до пятницы (даты нет)» в протоколе и в
  сообщении; ни даты, ни срока словами — «—» / «срок не определён».
- Человек не из участников 01 (ЛПР, владелец следующего шага, исполнитель, владелец
  риска) — первое предложение `observed_role` из `09.authority_observations` с пометкой
  «(не участник встречи)», иначе в протоколе `` `id` (не участник встречи) ``, в
  сообщении — «не участник встречи, имя не названо»; пометка — только у
  строк-идентификаторов (`^[a-z0-9][a-z0-9-]*$`), свободный текст вместо id — как есть;
  наблюдения копируются в `follow_up.json` (`authority_observations`).
- Обязательство с confidence ниже probable — в протоколе с пометкой «(требует
  подтверждения)», в сообщение не попадает.
- Только действующие договорённости: `related_mentions` обязательств (предложение,
  принятие, прежние версии) из `follow_up.json` убираются и в протокол и сообщение не
  попадают; уступки 05 (`prior_position_speaker`) follow-up не читает.

`manifest --meeting <id>` — `run_manifest.json`: версии и хеши контрактов, хеши
входов (исходники, 11 JSON, предложение, реестры, файлы движка), этапы,
`overall_status`, `resume_from`, применённые предложения.

### База знаний

`knowledge diff --meeting <id>` — читает `negotiations/<id>/knowledge_proposal.json`,
сравнивает с текущим `knowledge/` и пишет `knowledge_diff.md` (unified diff для
Markdown, таблица для записей реестров). Ничего не применяет. Проверки:
пути только внутри `knowledge/` (кроме `review_decisions.jsonl` и `events/`),
`create` не поверх существующего файла, `update` только существующего,
сохранение всех строк с пометкой `(m)`, `append` только нового id, `update` не
переводит в терминальный статус (для этого `close`). Код 1 при ошибках
предусловий — применение заблокировано. Рядом с diff пишется `knowledge_diff_snapshot.json` —
SHA-256 каждого файла и реестра, которые затронет apply.

Если в предложении есть раздел учёта `accounting[]` (см. ниже), diff дополнительно
проверяет полноту учёта и показывает раздел «Учёт объектов разбора»: сводку, группу
«Уверенные» (записываем · объединяем с чем · не переносим и почему) и группу
«Сомнительные» с решениями пользователя, а также блок «Вопросы пользователю — одним
блоком» по пунктам без решения. Diff показывает предложение **с наложенными решениями**:
отклонённое не вносится, переписанное — в новой формулировке, объединённое — как
обновление цели. В снимок пишутся хеш действующих решений (`decisions_sha256`) и хеши
файлов разбора 01/07/08/09 (`analysis_inputs`). В JSON-выводе — `warnings`,
`accounting` (сводка) и `pending_decisions` (сомнительные пункты без решения).
Предложение без `accounting` (прежний формат) — предупреждение «Учёт не заполнен»,
поведение прежнее.

`knowledge apply --meeting <id> --confirm` — применяет предложение: пишет md,
добавляет/обновляет записи, при `close` переносит запись из `open`/`active` в
`closed` с полями `closed_at`, `closed_source: user_confirmation`,
`closed_in_meeting_id` (история не удаляется), дописывает события в
`knowledge/events/ledger.jsonl` по `knowledge_event.schema.json`, пишет квитанцию
`knowledge_apply.json`, отмечает diff как применённый и пересобирает
`knowledge/index.md` (если он создан движком). Требует показанного diff того же
предложения (по SHA-256). Без `--confirm` — отказ (код 2). Если после показа diff
изменился любой затронутый файл или реестр (другой чат, ручная правка), apply ничего не
пишет и просит показать diff заново (код 1). Повторный apply того
же предложения ничего не дублирует (`status: already_applied`).
При заполненном учёте apply применяет уверенные пункты общим подтверждением, а
сомнительные — только с решением пользователя: нет решения хотя бы по одному
сомнительному пункту — отказ (код 2); решения изменились после показа diff — отказ
(код 2), нужен новый diff; изменились файлы разбора 01/07/08/09 — отказ (код 1).
Квитанция хранит сводку учёта и применённые решения (`history[].accounting`).

`knowledge decide --meeting <id> --item <ref|№> --decision accept|reject|rewrite|merge [--text "…"] [--target …]`
`knowledge decide --meeting <id> --list`

Записывает ответ пользователя по пункту учёта в
`negotiations/<id>/knowledge_decisions.jsonl` (только дописывание; `source:
user_confirmation`; строка привязана к SHA-256 текущего предложения — после
пересборки предложения прежние ответы не действуют и вопросы задаются заново). База не
меняется. `--item` — ref пункта или номер сомнительного пункта из diff; `--list` —
сомнительные пункты и решения по ним. Действует последнее решение по пункту; после
любого решения нужен новый `knowledge diff`.

| Решение | Что будет записано |
|---|---|
| `accept` | как в предложении |
| `reject` | цель пункта не применяется: запись реестра не вносится, фрагмент убирается из карточки, карточка без фрагмента не создаётся и не обновляется. Для пункта `skip` — «перенести всё-таки»: ответ сохраняется, а apply заблокирован до пересборки предложения |
| `rewrite --text` | новая формулировка: в записи реестра — поле `what` (обязательства), `description` (риски), `statement` (решения, поручения); во фрагменте карточки — замена строк. Цитата транскрипта не меняется |
| `merge --target` | только для пунктов `record`. Запись реестра: новая запись не создаётся, в цель того же реестра (`<id>` или `knowledge/….jsonl#<id>`) дописываются недостающие элементы списков (evidence, участники, организации), `last_seen_meeting_id` и ссылка в `merged_from`; статус и формулировка цели не меняются. Фрагмент карточки переносится в карточку-цель (`knowledge/….md#Раздел` — в конец раздела, иначе перед «Ручные заметки») |

Отказ (код 2): в предложении нет учёта; в предложении есть ошибки предусловий (ответы
привязаны к версии предложения — сначала исправить его); пункт неизвестен или учтён
дважды; решение несовместимо с судьбой пункта (`rewrite`/`merge` для `skip`, `merge`
для `merge`); цель пункта общая с другими пунктами и убрать её только для одного
нельзя; цель объединения не найдена; предложение уже применено.

Строка `knowledge_decisions.jsonl`:

```json
{"decision_id": "kd-…", "meeting_id": "…", "proposal_sha256": "…", "item": "risk:r-…", "decision": "merge", "text": null, "target": {"registry": "knowledge/risks/active.jsonl", "id": "r-…"}, "source": "user_confirmation", "recorded_at": "ISO-8601"}
```

Формат `knowledge_proposal.json` (готовит LLM-этап):

```json
{
  "meeting_id": "...",
  "generated_at": "ISO-8601",
  "contract_version": "1.1.0",
  "files": [
    {"path": "knowledge/people/<slug>.md", "action": "create|update", "content": "<полное новое содержимое>"}
  ],
  "records": [
    {"registry": "knowledge/commitments/open.jsonl", "action": "append|update|close", "id": "<id>", "record": {...}}
  ],
  "accounting": [
    {"ref": "<вид>:<id или №>", "fate": "record|merge|skip", "target": {"registry": "…", "id": "…"} | {"file": "…", "fragment": "…"}, "reason": "…", "certainty": "sure|doubtful", "question": "…"}
  ]
}
```

- `files`: только Markdown внутри `knowledge/`; `organizations/` — основной
  каталог, существующий файл в `companies/` используется как текущее состояние,
  запись идёт в `organizations/`.
- `records.action`: `append` — новая запись (`record` целиком); `update` —
  слияние полей поверх существующей; `close` — для парных реестров перенос в
  закрытый с терминальным статусом (`done|cancelled` для обязательств,
  `closed|realized` для рисков; по умолчанию `done`/`closed`), для одиночных
  реестров (`decisions`, `assignments`) — смена статуса на терминальный.
- `accounting` — полный учёт: каждый объект разбора получает ровно одну судьбу.

  | Объект | Откуда | `ref` | Учёт |
  |---|---|---|---|
  | Участник | `01.participants[]` | `participant:<person_id>` | обязателен |
  | Организация | `01.companies[]` | `organization:<id>` | обязателен |
  | Обязательство | `07.commitments[]` | `commitment:<id>` | обязателен |
  | Открытый вопрос | `07.open_questions[]` | `question:<№>` | обязателен |
  | Риск | `08.risks[]` | `risk:<id>` | обязателен |
  | Решение и ЛПР | `09.decision_areas[]` | `decision:<№>` | обязателен |
  | Полномочия (ЛПР) | `09.authority_observations[]` | `authority:<№>` | обязателен |
  | Нерешённое в карте решений | `09.unresolved[]` | `unresolved:<№>` | обязателен |
  | Тема, ключевой факт | `01.topics[]`, `01.key_facts[]` | `topic:<id>`, `fact:<№>` | по желанию |

  `<№>` — порядковый номер в списке файла разбора, с 1. Обязательность учёта следует
  профилю разбора встречи (`analysis_profile` в `review.yaml`): в `light` объекты 09
  не требуются и отсутствие 09 не предупреждение; артефакт вне профиля, если он всё же
  построен, учитывается по желанию. `fate`: `record` — записываем
  (цель обязана быть в этом предложении: `records[]` с тем же реестром и id или
  `files[]` с тем же путём); `merge` — объединяем с записью, которая уже есть в базе или
  в предложении; `skip` — не переносим. Для `merge` и `skip` обязательна `reason`.
  `target` — запись реестра `{"registry", "id"}` или карточка `{"file"[, "fragment"]}`;
  `fragment` — одна или несколько целых строк, встречающихся в содержимом карточки
  ровно один раз (указывается, когда в одной карточке сходятся несколько объектов, —
  тогда пункт можно отклонить или переписать отдельно). `certainty`: `sure` —
  применяется общим подтверждением, `doubtful` — только по решению пользователя;
  `question` — необязательная формулировка вопроса.
  Ошибки предусловий (apply заблокирован): объект разбора без пункта учёта; два пункта
  на один объект (двойной учёт); неизвестный `ref`; неверные `fate`/`certainty`;
  `merge`/`skip` без причины; цель `record` отсутствует в предложении; цель `merge` не
  найдена; фрагмент не найден, не уникален или не из целых строк. Изменения
  предложения без пункта учёта (темы, факты) перечисляются в diff отдельно.
- Пример — `templates/knowledge_proposal.template.json`.

### Очередь проверки

`review queue` — пересобирает `system/review_queue.{json,md}`: открытые пункты
`review.yaml`, непройденный шлюз, неподтверждённая карта спикеров, участники
`Speaker N`, выводы с `confidence possible|speculative`, обязательства без срока,
риски без владельца или срока, зависшие вопросы (`stalled_topic`,
`commitment_rescheduled`, `unanswered_promise` — правила в описании `control-center`).
Текст пункта зависшего вопроса включает число встреч или цепочку сроков, поэтому
после новой встречи без движения пункт возвращается в очередь с новым id.

`review record --item <rq-id> --decision <text> [--status closed|deferred]` —
дописывает решение в `knowledge/review_decisions.jsonl` с `source:
user_confirmation` и пересобирает очередь. Запись решения не меняет реестры:
изменение самой записи оформляется отдельным предложением.

### Конвейер и производные

`refresh --meeting <id> [--force]` — validate → report → followup → manifest для
одной встречи; при неизменных хешах входов готовая встреча переиспользуется.
Код 1 при сбое любого шага.

`refresh-all [--force]` — все встречи, очередь, синхронизация ledger (снимки
обязательств и рисков), проекция ledger и её сверка с реестрами, поисковый
индекс, `knowledge/index.md`, контрольный центр и его проверка →
`system/pipeline_run.json`. Код 0 только если все встречи `ready` и нет ошибок
целостности.

`status [--meeting <id>]` — состояние конвейера (этапы и `resume_from`) или
сводка по всем встречам; всегда код 0. Поле `workspace` и строка вывода — версия
схемы базы: `current`, `new` (папка пуста), `needs_migration` (с предупреждением
и командой `migrate`), `newer_than_plugin`, `invalid`. Ничего не создаёт.

`control-center [--as-of YYYY-MM-DD]` — `system/control_center.md` и `.json`:
сводка, системные возможности, просрочки, зависшие вопросы, риски высокой важности,
незавершённые встречи, открытые вопросы, реестры, целостность данных. Код 1 при
ошибках целостности. Раздел `stalled` (в `.md` — «Зависшие вопросы», отдельно от
просрочки): `topics` — тема или открытый вопрос нерешённые на ≥ 2 встречах
(открытый вопрос в 07, область решения в 09, статус темы `open|blocked|overdue` в
01) без решения `confirmed|rejected` в `decisions/register.jsonl` (связь — поле
`linked_topic|topic_id|topic|topics` или совпадение цитаты решения с цитатой
области решения); `rescheduled_commitments` — срок открытого обязательства менялся
≥ 2 раз (снимки журнала событий или повторные извлечения того же id на встречах);
`unanswered_promises` — открытое обещание другой стороны поднималось ≥ 2 раз на
более поздних встречах (тот же id в 07 или обновление записи по итогам встречи) без
результата. У каждого пункта — встречи, даты, цитаты, id пункта очереди и его статус.
В шапке — версия схемы базы; нужна миграция — предупреждение в целостности данных.

### Версия схемы и миграции

`migrate [--confirm]` — версия схемы рабочей папки в `knowledge/workspace.json`
(`schema_version`, `origin`, `created_at`, `plugin_versions`, `migrations_applied`).
Без `--confirm` печатает план и ничего не пишет; с `--confirm` применяет
идемпотентные миграции и повторно ничего не меняет (`status: nothing_to_do`).
`0001-record-schema-version` — создаёт файл версии для папки, созданной до 0.6.0
(`origin: legacy_folder`, `created_at: null`); `0002-name-variant-fields` —
добавляет во frontmatter карточек `people/`, `organizations/`, `companies/` пустые
`speech_variants: []` и `asr_variants: []`, не меняя остальных строк (страховка
проверяет, что кроме вставки ничего не изменилось; карточка без frontmatter
пропускается). Реестры, журнал и встречи не трогаются. Новая пустая папка получает
файл версии сама при первой записи (`source create`, `knowledge apply`,
`refresh-all`); туда же дописывается новая версия плагина. Код 2 — файл версии
повреждён или схема новее плагина.

### Ревью контрагента

`counterparty --org <id|название> [--since YYYY-MM-DD] [--until YYYY-MM-DD]` —
`system/counterparty/<org>.{md,json}` (производное). Организация — по id или
названию (карточка, `speech_variants`, разборы встреч; несколько совпадений — код 2
со списком). Люди — карточки с организацией в `organizations`, участники встреч с её

`document` (выполнено и есть документальное доказательство: `fulfillment_evidence`

папки-документа) / `user_words` (закрыто по подтверждению пользователя без документа)
/ `talk_only` (открыто или «выполнено» только в разборе) / `cancelled`; наши
обещания им с теми же группами, сроками, переносами; позиции по темам из

вопросы, зависшее; пробелы данных. Период: обещание входит, если дано не позже

«Данные:». Ничего не пишет в `knowledge/`.

`search "<запрос>" [--kind K] [--meeting ID] [--person ID] [--topic ID] [--limit N] [--any]`
— поиск по `system/search.sqlite` (FTS5; при его отсутствии в сборке SQLite —
резервный LIKE-поиск). Индекс строится автоматически, если его нет.

### Длинная встреча по частям и независимая проверка

Опора для агентов плагина (`agents/`): главный агент не читает длинный транскрипт целиком,
артефакты 01–08 по частям готовит `transcript-analyst`, независимую проверку делает
`evidence-verifier`. Порядок работы — `skills/meeting-analysis/SKILL.md`, разделы «Длинные
встречи» и «Режим с верификацией».

`parts plan --meeting <id> [--max-chars N] [--context N]` — делит `transcript.txt` на части по
границам реплик (строка с таймкодом или меткой говорящего открывает реплику, строка без них
продолжает её; реплика не режется) не больше `N` знаков (по умолчанию 25 000) и пишет
`analysis/parts/plan.json`: число реплик, знаков, длительность по таймкодам, признак `long` и
его причины (≥ 60 минут, ≥ 50 000 знаков или ≥ 500 реплик), части со строками `line_from`–`line_to`,
`context_from_line` (начало `N` реплик контекста, по умолчанию 3), таймкодами и объёмом, SHA-256
транскрипта. Текст транскрипта не печатает. Всегда код 0.

`parts check --meeting <id> [--file <часть>]` — файлы `analysis/parts/<NN>_<имя>.part-<K>.json`
(и `speaker_map_proposal.json`, если есть): `meeting_id`, контракт артефакта (пустой список в
части — предупреждение, обязательность списка проверяется у итога), цитаты модулем
`quote_check` (как в `validate`) и то, что опорная цитата пункта (`quote`, `source_quote`,
`evidence_quote`) лежит в строках своей части; прежняя позиция уступки, связанные реплики
обязательства (`related_mentions`) и доказательства личности участника (`participants[].evidence`)
могут быть вне части — предупреждение. Код 1 при ошибках.

`parts merge --meeting <id> [--artifact 07,08] [--force]` — сводит части каждого артефакта в
итоговый `analysis/<NN>_<имя>.json`: списки объединяются по порядку частей, точные дубликаты
снимаются, совпавшие `id` с разным содержимым переименовываются (`<id>-p<K>`, в выводе
`renamed_ids`); обязательства 07 сводятся по «той же записи» — совпадают `who`, `what`,
`source_quote`, `source_timestamp` и `deadline` (без учёта лишних пробелов): одна запись,
`related_mentions` объединяются без повторов по цитате и таймкоду (по порядку таймкодов,
пустое `note` дополняется из повтора), в выводе `joined` (части, сколько связанных реплик
добавлено, поглощённые `id`); если у той же записи различаются другие поля (`confidence`,
`status`, `to_whom`, `follow_up`, `id` …) — остаётся запись с большей уверенностью (при
равной — из более ранней части), расхождение — в `conflicts` с перечнем полей `differs`.
Не сводятся, а перечисляются в `possible_duplicates` (решает главный агент): записи одного
исполнителя с той же опорой, но другой формулировкой или сроком, и записи, где опора одной —
связанная реплика другой (повтор в итогах, записанный аналитиком поздней части как
отдельное обещание). Участники, организации и темы 01 сводятся по id (при расхождении остаётся
запись с большей уверенностью, расхождение — в `conflicts`); в 05 вопросы и перебивания
суммируются, доли речи взвешиваются по объёму частей, `dominant_speaker` — наибольшая доля; в 06
самый негативный и самый напряжённый момент — по точкам кривой (минимум valence, максимум
arousal). Поля о встрече целиком (исход, вывод, общий тон, контроль рамки) берутся черновиком из
последней части и перечисляются в `review_fields` — их утверждает главный агент. Существующий
итоговый файл без `--force` не перезаписывается (код 1 и пункт в `skipped`); код 1 и при
нарушении контракта итогом.

`verification check --meeting <id>` — проверяет `analysis/verification_report.json` (отчёт агента
`evidence-verifier`, сохранённый главным агентом без правок): `meeting_id`; вердикт каждой
находки — `confirmed | contradicted | changed_later | unsupported | missed`; `artifact` — файл
артефакта, `path` — существующий JSON-адрес в нём (для `missed` — список, куда относится
пропуск); у каждой находки цитата из транскрипта (модуль `quote_check`) и таймкод (если в записи
нет таймкодов — номер строки `line`); сводка `summary` совпадает с числом находок по вердиктам.
Правоту находок по существу не оценивает. Ничего не пишет. Код 1 при ошибках.

### Оценка разбора по несущему ядру

`eval --meeting <id> --core <core.json>` — сверяет разбор встречи (01, 05, 07, 08, 09 —
какие есть; иначе из `analysis_bundle.json`) с заранее зафиксированным ядром: каждый пункт
ядра получает FULL / PARTIAL / MISSING / DISTORTED с объяснением, отдельно — лишние находки,
противоречащие ядру (ложное «договорились», дубль, устаревшая версия, решение со слов
ИИ-ассистента, цитата без опоры). Пишет `negotiations/<id>/eval_result.json` и `.md`.
Сопоставление детерминированное, без LLM и без зависимости от `validate`. Код 0 — PASS (все
пункты ядра FULL, лишних искажений нет), 1 — FAIL, 2 — ядро не найдено, не прошло проверку
структуры или не подходит к транскрипту, нет артефактов. Методика, формат `core.json` и
реестр проверочных встреч `tests/evals/` — `docs/EVALS.md`.

### Упаковка артефактов

`bundle pack --meeting <id>` — все `analysis/*.json` + `source_packet.json` +
`run_manifest.json` (если есть) → `negotiations/<id>/analysis_bundle.json`
вида `{"bundle_version", "contract_version", "meeting_id", "packed_at",
"files": {"analysis/01_extraction.json": {...}, ...}, "checksums": {...}}`.
Нужно для хранения встречи несколькими документами проекта вместо 13 файлов.

`bundle unpack --meeting <id> [--force]` — восстанавливает файлы из пакета.
Совпадающие файлы не трогаются; файл, изменённый позже `packed_at`, без
`--force` пропускается (код 1 и список пропущенных). `contract_version` пакета не
сверяется: пакет 1.0.0 читается движком с контрактами 1.1.0 как есть (в 1.1.0 добавлены
только необязательные поля), проверка — обычным `validate` после распаковки. Пакет
1.1.0 с новыми полями (`related_mentions` и др.) движок с контрактами 1.0.0 распакует, но
`validate` отвергнет — нужна версия плагина с контрактами 1.1.0.

### Отправка себе

Только самому пользователю (решение владельца); подробности — `skills/negotiation-system/references/delivery.md`.

| Команда | Что делает |
|---|---|
| `deliver setup --email <адрес>` | адрес почты для писем себе |
| `deliver setup --telegram-token-stdin` | ключ бота одной строкой со стандартного ввода → `delivery/secrets/` (сам ключ не печатается) |
| `deliver setup --forget-telegram` / `--forget-email` | отвязать чат и очистить ключ / забыть адрес |
| `deliver telegram-link [--chat <id> --confirm]` | показать личные чаты, писавшие боту; привязать свой (группы и каналы не привязываются). Ходит в сеть |
| `deliver status` | настройки, источник ключа, ожидающие показы, последние отправки |
| `deliver preview --file <файл> --channel telegram\|email [--mode auto\|text\|file]` | показ: кому, что, сколько частей, отпечаток, предупреждения шлюза; пишет `delivery/pending/` |
| `deliver send --file <файл> [--channel telegram] --confirm [--again] [--resend-unknown]` | отправка в Telegram показанного (сверка по отпечатку); Markdown → HTML Telegram, длинное — файлом. Ходит в сеть |
| `deliver record --file <файл> [--channel email] --status draft\|sent\|failed\|unknown [--ref <id>] [--again]` | исход письма себе после действия подключения Gmail |
| `deliver log [--limit N]` | журнал отправок |

Повтор уже отправленного — только `--again`; после исхода `unknown`/`partial` — только
`--resend-unknown` (пользователь проверил чат). Отправлять можно любой файл рабочей папки, кроме
`delivery/`. Переменные: `NA_TELEGRAM_BOT_TOKEN` (ключ), `NA_TELEGRAM_API_BASE`, `NA_TELEGRAM_TIMEOUT`.
Коды: 0 — отправлено; 1 — не отправлено (нет показа, показ устарел, повтор без флага — записи в
журнале нет) или попытка была, но не удалась или исход неизвестен (запись в журнале есть); 2 —
ошибка использования.

### Самопроверка

`doctor [--probe]` — без сети: версия и кодировка Python (с `--probe` — какие команды `py -3`,
`python3`, `python` реально запускают Python ≥ 3.10), сверка файлов с паспортом сборки
`BUILD-MANIFEST.json` (у `SKILL.md` — тело без YAML-шапки), описание хуков и агентов, версия схемы
и настройки отправки рабочей папки, защита ключа бота, соседний плагин Ивана. Код 1 — есть ошибки.

### Аудио (опционально)

`audio --check` — сообщает, какие зависимости отсутствуют (`numpy`, `soundfile`,
`librosa`); код 2, если слой недоступен. Остальные команды от них не зависят.

`audio --meeting <id> --wav <file> --segments <segments.json>` — инструментальные
метрики сегментов (`start_ms`, `end_ms`, `speaker`, `text`) →
`analysis/audio_acoustic_metrics.json`. Метрики не содержат смысловых или
клинических выводов и не меняют текстовый анализ.

## Коды выхода

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | проверка не пройдена: схема, цитаты, полнота отчёта, ошибки предусловий diff, целостность, незавершённые этапы в `refresh-all`, пропуски в `bundle unpack` |
| 2 | ошибка предусловия или использования: нет файла или встречи, дубликат источника, `apply` без `--confirm` или без показанного diff, `apply` без решения по сомнительному пункту или после нового решения без нового diff, неизвестный пункт очереди или учёта, несовместимое решение `knowledge decide`, недоступный аудиослой |

С `--json` ошибка печатается как `{"valid": false, "error": "...", "exit_code": N}`.

## Инварианты

- Обязательство, риск, решение и пункт очереди не закрываются без решения
  пользователя: закрытие — только через `knowledge apply --confirm` с `close`
  или `review record`.
- Строки с пометкой `(m)` в файлах `knowledge/` обязаны сохраниться в
  предложении, иначе diff и apply блокируются.
- При заполненном учёте каждый объект разбора получает ровно одну судьбу;
  сомнительный пункт не применяется без ответа пользователя, а любой новый ответ
  требует нового diff (снимок связывает diff с хешем решений).
- `knowledge/events/ledger.jsonl` — только дописывание; проекция
  `system/event_projection/` сверяется с реестрами при каждом `refresh-all`.
- Всё в `system/` производно и пересобирается; `knowledge/index.md`
  пересобирается только если создан движком (есть маркер `generated by na.py`).
- Ошибка схемы или цитаты блокирует `ready`; follow-up всегда `draft_not_sent`.
- Движок не ходит в сеть и не читает секреты из файлов проекта; исключение — `deliver telegram-link` и
  `deliver send` (API Telegram, ключ из переменной или `delivery/secrets/`).

## Совместимость с прежним рабочим каталогом

Читаются устаревшие поля: `personal_data.processing_consent: true` в
`review.yaml` считается `consent=yes`; `note_plaud.md`/`source_note.md`
учитываются в хешах входов; `knowledge/companies/` читается как организации.
Встреча без `source_packet.json` проверяется с предупреждением.
