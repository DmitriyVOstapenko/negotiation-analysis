# Разбор по методике Арти Галиева

Это штатный этап **полного** анализа после проверки основных артефактов 01–11, до отчёта.
Пользователь уже выбрал его вместе с полным профилем: не спрашивать, нужен ли этот разбор,
можно ли оценивать владельца и нужно ли отдельно сохранять совет. Лёгкий профиль этот этап
не выполняет. Методический вывод — интерпретация поведения в эпизоде, а не новый факт о человеке.

## 1. Данные и граница метода

Прочитать целиком [Negociar-RU](../../negociar-ru/SKILL.md) и его
[полный контракт](../../negociar-ru/references/workflow.md). Взять из него метод канона,
поиск случаев, проверку собственной стороны и уважительный тон. Формат отдельной консультации
(четыре блока ответа, уточняющие вопросы, ролевая игра) не заменяет этот этап отчёта.
Подробная стратегия будущего разговора и дословное сообщение остаются отдельным запросом.

Фактура: проверенные 01–11, карта участников, подтверждения владельца и точечное чтение
транскрипта для проверки эпизодов. Применять согласованные исключения и маскирование.
Не возобновлять шлюз, не регистрировать источник заново и не запрашивать повторную карту
спикеров. Неподтверждённая личность или неясная реплика ограничивает оценку, а не разрешает догадку.
Зафиксировать время встречи и известное окно следующего действия; неизвестное назвать прямо.

## 2. Прочитанный канон и реальные случаи

Для ключевых эпизодов выбрать домены по таблице Negociar-RU. **Прочитать соответствующие
файлы канона**, а при сквозном принципе — `00-ARQUITECTURA.md`. Команда `--canon` печатает
путь: это ещё не чтение файла. Путь `PLUGIN` и Python выбрать по SKILL.md среды.

```text
python "PLUGIN/skills/negociar-ru/scripts/buscar.py" --canon D4
python "PLUGIN/skills/negociar-ru/scripts/buscar.py" "слова проверяемого эпизода" --dom D3,D8 --n 6
python "PLUGIN/skills/negociar-ru/scripts/buscar.py" --show N
```

Домен и слова в примере заменить по ситуации. По найденным кандидатам прочитать через
`--show` полные случаи и блоки «Разбор» у 2–3 первых подходящих кандидатов; предпочитать
случаи с разбором Арти. Слабый результат — переформулировать запрос или снять фильтр.
Поисковый фрагмент не заменяет прочитанный случай. Не подменять метод общими советами.

Сохранить фактически использованные запросы и ссылки. Для принципа — точное имя файла
из `data/canon/` (только имя файла), точный заголовок прочитанного раздела без Markdown-знаков
`#` и короткую дословную выдержку из этого раздела. Для случая —
номер `N` из `--show`, его реальные `id` и `title`; `id` занятия не заменяет номер случая.
Объяснить, чем случай помогает понять эпизод и чем отличается: аналогия не доказывает мотив.
Если подходящего случая после поиска нет, явно указать это и опереться на применимый
прочитанный принцип. Не выдумывать прецедент ради заполнения поля. Нет применимого принципа —
для соответствующего участника `insufficient_evidence` с этим конкретным пределом метода в
`limitations`; не выдавать общий совет за канон и не подставлять нерелевантную ссылку.

## 3. Оценка всех участников

Каждого человека из `01_extraction.participants` включить ровно один раз, включая владельца
и его сторону. ИИ-ассистент в участники не входит. Не присваивать людям постоянные черты,
диагнозы или скрытые намерения. Оценивать конкретные ходы, без автоматической защиты своей стороны.

Для каждого, где достаточно материала:

- назвать наблюдаемый ход с дословной цитатой и таймкодом его реплики;
- объяснить интерпретацию простыми словами: что помогло, где участник уступил управление
  разговором, оставил неясность или мог не заметить свою ошибку; не требовать наличия ошибки;
- связать вывод с прочитанным принципом и подходящим случаем; отделить наблюдение от гипотезы;
- дать альтернативное объяснение того же эпизода, ограничения и степень уверенности словами;
- предложить следующий ход с его целью, вероятным возражением, ответной развилкой и способом
  проверить результат; указать цену: время, уступку, риск отношений или другое последствие;
- обозначить неблагоприятный сценарий и обратимое деловое действие, если основной ход не сработает.

Если реплик мало, нет надёжной атрибуции или они не дают основания для методической оценки,
поставить `insufficient_evidence`, объяснить конкретный пробел в `limitations`. Не дописывать
оценку, цитату, принцип или совет для симметрии. Для остальных участников продолжить разбор.
Существенный пробел показать в ограничениях отчёта; неритуальный вопрос владельцу нужен,
только если ответ действительно меняет рекомендацию. Неполные данные допускают условные ходы.

## 4. Артефакт и проверка

Сохранить `ROOT/negotiations/<id>/analysis/12_galiev_review.json`:

```json
{
  "meeting_id": "<id>",
  "method": "negociar-ru",
  "transcript_sha256": "<SHA-256 текущего transcript.txt>",
  "summary": "<методический вывод, обозначенный как интерпретация>",
  "principles": [{"file": "<имя файла канона>", "heading": "<точный заголовок>", "source_quote": "<точная короткая выдержка>"}],
  "cases": [{"number": 1, "id": "<реальный id>", "title": "<реальное название>", "relevance": "<сходство>", "difference": "<различие и предел аналогии>"}],
  "case_search": {"queries": ["<фактически выполненный запрос>"], "no_match_reason": null},
  "participants": [{
    "participant_id": "<id из 01>",
    "status": "assessed",
    "assessment": "<наблюдение, интерпретация и уверенность>",
    "alternative": "<альтернативное объяснение>",
    "evidence": [{"quote": "<цитата из транскрипта>", "timestamp": "HH:MM:SS"}],
    "principle_refs": [0],
    "case_refs": [1],
    "next_steps": [{"action": "<ход, цель и развилки>", "tradeoff": "<цена и риски>"}],
    "limitations": ["<ограничения вывода>"]
  }],
  "limitations": ["<общие ограничения>"]
}
```

Это схема заполнения, не готовый разбор: заменить все примеры фактическими значениями,
добавить остальных участников. `principle_refs` — индексы массива `principles` с нуля;
`case_refs` — глобальные номера случаев библиотеки, перечисленные в `cases`. При отсутствии
подходящих случаев — `cases: []`, соответствующие `case_refs: []` и непустой
`case_search.no_match_reason`. Участник без достаточных оснований: `status: "insufficient_evidence"`,
непустой список строк `limitations`, `assessment` и `alternative` — `null` или пустая строка,
`evidence`, ссылки и `next_steps` могут быть `[]`, без вымышленных доказательств.
Таймкод — `HH:MM:SS` или `MM:SS`; `null` допустим только при отсутствии таймкодов во всём
транскрипте и с явной оговоркой об этом ограничении. Не менять контракты основных 11 файлов.

Проверить SHA-256 текущего неизменённого транскрипта, точность цитат и ссылок, затем выполнить
`na.py --root ROOT report --meeting <id>`: команда проверяет 12 перед созданием отчёта;
`validate` отдельно проверяет только основные 11 файлов. Требование нового полного разбора записывается
движком в `review.yaml → galiev_review: {required: true, source: plugin_default, policy_version: 1}`.
Не снимать этот маркер ради прохождения проверки. Не называть полный разбор готовым,
пока проверка обязательного артефакта не пройдена. Общий процесс при `refresh` также проверяет
12 и наличие содержательной методической главы в окончательном `report.md`.
Наличие JSON не доказывает качество
методической интерпретации или фактическое чтение канона.

## 5. Отчёт и сохранение

В `report_auto.md` и окончательном `report.md` сохранить отдельную главу
**«Разбор по методике Арти Галиева»**. Краткий главный вывод включить в первый экран.
В главе объяснить метод одним предложением, затем разобрать участников, применимые принципы,
аналогии с различиями, ходы с ценой и ограничения. Истории рассказать понятно, не заменять
объяснение кодами доменов и номерами случаев; технические ссылки остаются в JSON.

Раздел — часть отчёта встречи, сохранение которого уже входит в полный анализ. Не запускать
отдельный вопрос о сохранении стратегии, не создавать `advice/` или индекс стратегий.
Интерпретации из 12 не переносить как свойства людей в `knowledge/` и не включать в протокол
или сообщение другой стороне. Изменения базы по фактам — только обычным подтверждаемым
порядком `knowledge-update`; отдельная стратегия и её архив — по `conversation-strategy`.

Старые завершённые встречи автоматически не пересматривать. Когда владелец просит повторный
полный анализ существующей встречи, сначала выполнить
`na.py --root ROOT profile set --meeting <id> --profile full`, затем проверить 01–11 и выполнить этот этап; прежние согласие и карта
сохраняются в пределах той же записи. После этого пересобрать отчёт обычным порядком.
