# Разбор встречи

Цель: из сырого транскрипта получить проверяемый разбор, где каждый существенный вывод
опирается на цитату с таймкодом, и подготовить — но не применить — изменения базы знаний.
Правила доказательности, шлюз источника и хранилище — в навыке `negotiation-system`
(применять обязательно).

## Вход

Минимум — текст транскрипта (вставлен в чат, файл, документ проекта или запись из
подключённого источника). Желательно: дата встречи, цель, кто с нашей стороны, заметка
провайдера (`note.md`). Если транскрипта нет, а есть только резюме провайдера — сказать, что
разбор по резюме даёт только интерпретации без доказательств, и предложить получить
транскрипт.

## Порядок — выполнять по шагам, не пропуская

**Шаг 0. Хранилище.** Определить режим по `negotiation-system/references/store-adapter.md`
(папка / проект / только разговор). `ROOT` — корень рабочего каталога.

**Шаг 1. Шлюз источника.** До чтения содержания задать блок вопросов из
`negotiation-system/references/privacy-gate.md`. Если профиль `policy.yaml` даёт значения по
умолчанию — предложить их, но получить подтверждение для этой записи. При отсутствии
согласия — остановиться (`blocked_by_gate`).

> **Пути.** Claude Code сам подставляет путь к плагину вместо переменной `CLAUDE_PLUGIN_ROOT` (со знаком доллара и в фигурных скобках) в тексте этого файла. Если в команде переменная осталась как есть (другой хост) или команда взята из справочного файла (там написано `<корень плагина>`), подставь путь сам: корень плагина — на два уровня выше каталога этого навыка (`Base directory for this skill` → `…/skills/<навык>` → корень). Переменная окружения в Bash пуста — не полагайся на неё.

**Шаг 2. Регистрация.** Сохранить транскрипт в файл без изменений и выполнить:
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT source create --meeting <YYYY-MM-DD-slug> --transcript <файл> [--note <файл>] [--provider manual|plaud|wonderscribe|local_file|uploaded_transcript|document] [--captured-at <ISO>] [--title "..."]
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT source gate --meeting <id> --consent yes --masking <…> --sensitivity <…> --routes <…> --retain-source <yes|no>
```
Отказ по дубликату (`content_sha256` совпал) — спросить, продолжать ли существующую встречу.
Заполнить `meta.yaml`: дата, тип встречи, цель, наша сторона — из слов пользователя; чего
не знаем — `unknown`. Дату встречи не подставлять «сегодня»: если её нет ни в словах
пользователя, ни в источнике — дата файла с пометкой `requires_confirmation`. Затем, не читая
транскрипт, проверить объём: `na.py parts plan` (раздел «Длинные встречи»).

**Шаг 3. Карта спикеров и границы.** Применить промпт B.1 (`references/analysis-prompts.md`):
предложить соответствие `Speaker N → имя/роль` с доказательствами (самопредставление,
обращение по имени) и confidence. Если база есть — сверить имена из речи с `speech_variants` и
`asr_variants` карточек (распознавание часто искажает фамилии): совпадение варианта — повод
предложить соответствие, а не записать его. Показать пользователю, попросить подтвердить или поправить.
Спросить про исключаемый фрагмент (разговоры до/после встречи → `excluded_source_range`: `from`,
`to` или `null` — до конца записи, `reason`). Записать:
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT speakers set --meeting <id> --map "Speaker 1=Имя Фамилия (роль);Speaker 2=…"
```
Если пользователь недоступен для подтверждения — `speakers set` не вызывать (он записывает
подтверждение пользователя): работать с предложенной картой, записать её в `review.yaml` как
`speaker_mapping.status: proposed` (`source: null`) — пункт «подтвердить карту» очередь добавит сама.
Проверка цитат при неподтверждённой карте даёт по атрибуции предупреждения, а не ошибки. Нет меток
говорящих — карта тоже `proposed`, атрибуция не выше `probable`. ИИ-ассистент среди говорящих — не
участник: метка и роль — в `transcript_quality.known_issues`, его реплики — материал, а не решения людей.

**Владелец недоступен** (разбор без собеседника). Остальные вопросы к нему — в `review.yaml →
open_review_items`: список строк, каждая — один вопрос с вариантами ответа («подтвердить / поправить: …
/ не знаю»). Очередь (`na.py review queue`, контрольный центр) подхватит их с приоритетом high.
`review record` и `review confirm` записывают ответ владельца — без него не вызывать.

**Шаг 4. Контекст базы.** Прочитать из `ROOT/knowledge/` карточки упомянутых людей,
организаций, тем и реестры обязательств и рисков — чтобы использовать существующие `id`,
не создавать дубликатов и заметить повторяющиеся тактики. База пуста — так и сказать.

**Шаг 5. Восемь артефактов.** Последовательно, по методу из `references/analysis-prompts.md`
и строго по полям из `references/contracts-map.md`, создать `ROOT/negotiations/<id>/analysis/`:
`01_extraction.json` → `07_commitments.json` → `08_risks.json` → `02_tactics.json` →
`03_manipulations.json` → `04_arguments.json` → `05_power.json` → `06_emotions.json`.
Для каждого файла перед записью проверить самому: каждая цитата скопирована из транскрипта
буквально; `meeting_id` совпадает; неизвестное — `null`; слабые сигналы — в `debug_possible`,
а не в основной список; манипуляции ниже порога (confidence < probable или severity < medium)
— только в очередь проверки. Аудио не анализировалось → `06_emotions.source: "text_only"` и
честные `limitations`. Длинная встреча — артефакты 01–08 по частям (раздел «Длинные встречи»).
Опора обязательства и особые случаи (ИИ-ассистент, нет разметки, год в дате, ЛПР только по должности,
одно обещание из нескольких частей) — `negotiation-system/references/evidence-rules.md`.

**Шаг 6. Три производных представления.** `09_decision_authority.json`,
`10_argument_map.json`, `11_meeting_effectiveness.json` — только из содержимого 01–08, без
новых цитат «по смыслу». ЛПР — только по сказанному, иначе `null` и пункт в `unresolved`.
`current_state` начинается со статуса: «Принято: …», «Не решено: …», «Отложено: …», «Отменено: …» — по
префиксу отчёт отличает принятое от открытого (без префикса решение считается открытым).
Оценка эффективности — рабочая диагностика с прозрачной формулой, не тест.

**Шаг 7. Валидация.**
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT validate --meeting <id>
```
`valid: false` → исправить артефакты (не транскрипт!) и повторить. Чаще всего ломаются цитаты:
взять точный фрагмент из `transcript.txt`. Склейка реплик разных говорящих, цитата, приписанная не
тому человеку, и таймкод начала чужой реплики — тоже ошибки; цитаты «после нормализации» и с «…»
допустимы, но помечаются — по возможности заменить дословными (правила —
`negotiation-system/references/evidence-rules.md`, «Цитаты и таймкоды»). Не объявлять разбор
готовым при ошибках. В режиме с верификацией после `valid: true` — независимая проверка (раздел
«Режим с верификацией»).

**Шаг 8. Отчёт.**
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT report --meeting <id>
```
Прочитать `report_auto.md`, написать `report.md` — финальную редакцию: тот же состав, но с
тремя явно отделёнными слоями: факты транскрипта (с цитатами) · интерпретации и гипотезы (с
confidence) · подтверждения пользователя (`source: user_confirmation`). Структура — в
`references/report-format.md`; первая строка — **Данные:** (источник, качество, разметка
говорящих, дата базы, чего нет). Перед выдачей «одного экрана» — проверка читателем: текст
перечитывается без источников. В Claude Code и Cowork — агент `negotiation-analysis:reader`: текст
«одного экрана» и отчёта передаётся ему в задании целиком, файлов и инструментов у него нет. В
проекте claude.ai и там, где агентов нет, — самому, не заглядывая в источники. Понятно ли, что
решить; какие места непонятны; оценка от 1 до 10, ниже 8 — одна правка этих мест.

**Шаг 9. Follow-up.**
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT followup --meeting <id>
```
Проверить `follow_up_protocol.md` и `follow_up_message.md`: ничего, что не подтверждено;
статус `draft_not_sent`; другой стороне ничего не отправлять — письмо отправляет сам пользователь.

**Шаг 10. Проект изменений базы.** Перейти к навыку `knowledge-update`: он формирует
`knowledge_proposal.json`, показывает `knowledge_diff.md` и ждёт подтверждения. Без
подтверждения память не меняется. После применения — `na.py refresh-all`, `na.py manifest`,
запись в проект (режим проекта).

## Лёгкий разбор

**Когда предлагать.** Пользователю нужно только «кто что обещал и какие риски»: рабочая или
статусная встреча, протокол по записи, поток однотипных встреч, длинная запись, где полный разбор
не окупается. Для переговоров с внешней стороной, конфликта, подготовки к следующему раунду — полный
разбор (там важны тактики, ЛПР, позиции). Спросить одной строкой в блоке вопросов шага 1: «Разбор
полный или лёгкий (только обязательства и риски)?»

**Что выходит.** Шаги 0–4 и 7–10 те же: шлюз, карта спикеров, проверка цитат, отчёт, follow-up,
проект изменений базы. На шаге 5 — только `01_extraction.json` → `07_commitments.json` →
`08_risks.json`; шаг 6 не выполняется. Профиль записать до валидации:
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT profile set --meeting <id> --profile light
```
В проекте claude.ai без скриптов — в `review.yaml`: `analysis_profile: {mode: light, source:
user_confirmation}`. Отчёт: один экран без оценки встречи и карты решений (вместо «Требуемого
решения» — открытые вопросы из 07) и раздел «Не выполнялось по профилю». В базу идут участники,
организации, темы, обязательства и риски; решений и ЛПР лёгкий разбор не даёт. Пользователю сказать
прямо: тактики, аргументация, карта решений и оценка встречи **не выполнялись** — это не «ничего не
найдено».

**Как перейти к полному.** `na.py profile set --meeting <id> --profile full` → шаги 5–6 для
недостающих артефактов (02–06, затем 09–11; 01/07/08 перепроверить) → `na.py refresh --meeting <id>`.
До этого встреча стоит на `resume_from: analysis_complete`. Если новые артефакты меняют вывод
(например, назван ЛПР) — новое предложение изменений базы.

## Длинные встречи

**Порог.** После регистрации (шаг 2), не читая транскрипт:
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT parts plan --meeting <id>
```
Команда печатает только счётчики — реплики, знаки, длительность по таймкодам, части по границам
реплик (до 25 000 знаков, реплика не режется) — и пишет `analysis/parts/plan.json`. Встреча
длинная (`long: true`), если она идёт 60 минут и дольше, или в ней 50 000 знаков и больше, или 500
реплик и больше. Короткая встреча — обычный порядок шагов.

**Claude Code и Cowork — главный агент транскрипт целиком не читает.** Из транскрипта ему нужны
только первые строки, чтобы увидеть формат меток. Он ведёт разговор (шлюз, карта спикеров,
вопросы), собирает карточку встречи и читает только JSON. Артефакты 01–08 делает агент
`negotiation-analysis:transcript-analyst`; ему передаются пути и задание, а не текст транскрипта.

1. **Карта спикеров.** Задание агенту «карта спикеров» по части 1 (представляются обычно в начале)
   → `analysis/parts/speaker_map_proposal.json`. Дальше шаг 3 как обычно: показать, получить
   подтверждение, `speakers set`.
2. **Карточка встречи** — один раз: дата, цель, наша сторона; подтверждённая карта спикеров
   (метка → имя, роль, `person_id`); id людей, организаций и тем из базы (шаг 4); исключённый
   фрагмент; режим маскирования из шлюза. Агенты не видят правил этого навыка — основные правила
   доказательности и маскирования записаны в их собственном тексте, карточка даёт им данные.
3. **Части.** По каждой части плана — одно задание: `ROOT`, `meeting_id`, карточка,
   `line_from`–`line_to` и `context_from_line` из плана, артефакты 01–07 (лёгкий разбор — 01 и 07),
   пути выхода `analysis/parts/<NN>_<имя>.part-<K>.json`. Части независимы — задания можно
   запускать параллельно.
4. **Проверка частей:**
   ```
   python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT parts check --meeting <id>
   ```
   Контракт, цитаты (тем же модулем, что и validate) и то, что опорная цитата каждого пункта лежит в
   своей части. Ошибки — новым заданием той же части с их перечнем; транскрипт главный не открывает.
5. **Слияние:**
   ```
   python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT parts merge --meeting <id>
   ```
   Итоговые `analysis/01…07`: списки объединяются, точные дубликаты снимаются, совпавшие id
   переименовываются (с сообщением), участники, организации и темы сводятся по id, вопросы и
   перебивания суммируются, доли речи взвешиваются по объёму частей, самый негативный и самый
   напряжённый момент берутся по точкам кривой. Обязательство 07, записанное в нескольких частях
   с той же опорой, сводится в одну запись с объединёнными `related_mentions`; `possible_duplicates`
   в выводе (та же опора, другая формулировка или срок) главный сводит сам на шаге 6. Уже
   существующий итоговый файл без `--force` не перезаписывается.
6. **Сведение по встрече целиком — главный, по итоговым JSON.** Поля из `review_fields` (исход,
   вывод о манипуляциях, общий тон, контроль рамки) утвердить или переписать с учётом всех частей.
   Одно обязательство в двух частях, позднее изменение или отмена — по цитатам и таймкодам; если
   нужен источник — точечное задание агенту на диапазон строк.
7. **Риски.** `08_risks.json` — задание агенту по готовым 01–07 (транскрипт — только вокруг
   используемых цитат) с записью сразу в `analysis/08_risks.json`.
8. **Дальше** — шаг 6 (09–11 главный делает из JSON), шаг 7 и далее обычным порядком.

Маршрут обработки, разрешённый шлюзом, не меняется: агенты работают в той же сессии и у того же
провайдера модели, что и главный.

**Проект claude.ai (нет агентов, нет скриптов).** Прежний путь: транскрипт читается
последовательно кусками, артефакты — по порядку шага 5. Для длинной встречи честно предупредить, что
разбор займёт несколько ответов, и предложить выполнить его в Claude Code или Cowork либо выбрать
лёгкий разбор.

## Режим с верификацией

**Когда.** По просьбе пользователя («проверь разбор независимо», «с верификацией») или по
предложению одной строкой в блоке вопросов, если в 07/08 есть подписание договора, платёж, сумма
(`value_rub`) или риск `high`. Включает пользователь.

**Как — Claude Code и Cowork.** После шага 7 (`valid: true`) — задание агенту
`negotiation-analysis:evidence-verifier`: `ROOT`, `meeting_id`, карточка встречи (с режимом
маскирования), объём проверки (по умолчанию 07, 08, 09 и участники 01). Агент ничего не исправляет и файлов не пишет — возвращает
JSON-отчёт. Сохранить его без правок как `analysis/verification_report.json` и проверить:
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT verification check --meeting <id>
```
Находка без цитаты, цитата не из транскрипта, адрес поля не найден — отчёт не принимается: вернуть
агенту перечень ошибок новым заданием.

**Как показывать находки.** На первом экране — строка «Независимая проверка: проверено N;
противоречит источнику N, изменено позже N, без опоры N, пропущено N». Находки `contradicted`,
`changed_later` и `missed` по обязательствам, срокам, суммам, ЛПР и рискам `high` — сразу на
первом экране, каждая с цитатой и таймкодом. Остальные — в разделе отчёта «Что требует проверки»
и вопросами пользователю одним блоком с вариантами ответа. Артефакт по находке главный правит,
только сверив указанное место транскрипта сам (точечным чтением диапазона строк) и только если
источник однозначен; иначе — вопрос пользователю. После правки — шаг 7 заново, а в отчёте —
пометка «исправлено по независимой проверке».

**Проект claude.ai.** Независимого проверяющего нет — сказать об этом прямо. По просьбе —
самопроверка по тем же правилам (вердикт, цитата, таймкод, адрес поля) отдельным проходом с
пометкой «самопроверка, не независимая».

## Ответ пользователю

Сначала один управленческий экран (из 09/11/07/08 и ключевых фактов 01):

1. Главный вывод встречи и её исход (`outcome`).
2. Что требует решения пользователя — пункты `review.yaml` и очереди (карта спикеров, выводы с
   низкой уверенностью, противоречия, нераспределённые ЛПР).
3. Ключевые факты и обязательства — кто, что, когда, цитата + таймкод.
4. Риски и противоречия — сначала high.
5. Варианты по открытым вопросам.
6. Следующий шаг (обычно: подтвердить спорное → применить изменения базы → follow-up).

Затем перечислить, какие детали подготовлены (тактики, манипуляции, аргументация, динамика
власти, эмоциональная кривая, карта решений, оценка эффективности) и спросить, раскрыть ли.
Критические факты и высокие риски — всегда на первом экране. Где анализа не хватает (нет
аудио, нет таймкодов, плохая расшифровка на 12:00–30:30) — сказать прямо, с влиянием на
выводы.

Если отправка себе настроена (`na.py deliver status`), в конце одной строкой предложить:
«Отправить отчёт себе в Telegram или на почту?» — и действовать по `negotiation-system` §10.

## Чего не делать

- Не выводить обязательства, решения и мотивы «по смыслу» без цитаты.
- Не назначать ЛПР и исполнителей по должности.
- Не считать «посмотрим», «подумаем» обязательством; не вычислять дату из «позже».
- Не писать в `knowledge/` напрямую — только через `knowledge-update` и подтверждение.
- Не редактировать `transcript.txt`; исправления — в `review.yaml` как подтверждения пользователя.
- Не предлагать стратегию «как ответить» внутри разбора — это навык `conversation-strategy`,
  и он включается по запросу.
