# Обновление накопительной базы

Здесь происходит накопление опыта: карточки людей, организаций и тем, реестры обязательств,
решений, поручений и рисков, журнал событий. Правило одно: **сначала проект изменений и
diff, потом явное «да» пользователя, только потом запись.** Правила доказательности и
хранилище — из навыка `negotiation-system`.

## Источники изменений

- Готовый разбор встречи (`negotiations/<id>/analysis/*.json` после `validate` = valid).
- Слова пользователя («Иванов вчера попросил отсрочку на две недели») — записывать как
  EvidenceRef с `source: user_confirmation` и датой, не как факт транскрипта.
- Документ или переписка — после шлюза источника (`negotiation-system/references/privacy-gate.md`).

## Порядок

**1. Прочитать текущее состояние.** Карточки `knowledge/people/`, `organizations/`, `topics/`,
`tactics_observed/` по упомянутым сущностям; реестры `commitments/open.jsonl`,
`risks/active.jsonl`, `decisions/register.jsonl`, `assignments/register.jsonl`;
`review_decisions.jsonl`. В режиме проекта — загрузить их в `ROOT` по
`store-adapter.md`. Если базы нет — создать структуру (`na.py status` создаёт каталоги).

**2. Сопоставить сущности.** Person — по нормализованному имени + организации, с учётом
`speech_variants` и `asr_variants` карточки; Organization — по ИНН или slug (и вариантам названия
в речи); Topic — по slug. Совпадение только по варианту — вопрос, не слияние. Новый вариант
имени, замеченный во встрече, предложить дописать в карточку через `files[]`. Совпадение → существующий `id`. Сомнение (однофамилец,
похожее название) → не сливать, вынести вопрос. Новая сущность → новый slug латиницей.

**3. Извлечь кандидатов** по `references/knowledge-update.md`: факты с EvidenceRef; новые или
уточнённые люди, организации; решения (принятые / отклонённые / отложенные / заменённые) и
мотивы отдельно; поручения с исполнителем, контролёром, сроком, результатом, критерием
приёмки; обязательства обеих сторон; риски, возможности, инциденты; позиции и влияние;
открытые вопросы и блокеры; наблюдения тактик (порог «типовой» — ≥ 2 встречи, ≥ probable);
рабочие гипотезы — только с альтернативами и confidence. Что не считать подтверждённым —
там же.

> **Пути.** Claude Code сам подставляет путь к плагину вместо переменной `CLAUDE_PLUGIN_ROOT` (со знаком доллара и в фигурных скобках) в тексте этого файла. Если в команде переменная осталась как есть (другой хост) или команда взята из справочного файла (там написано `<корень плагина>`), подставь путь сам: корень плагина — на два уровня выше каталога этого навыка (`Base directory for this skill` → `…/skills/<навык>` → корень). Переменная окружения в Bash пуста — не полагайся на неё.

**4. Собрать `negotiations/<id>/knowledge_proposal.json`** (формат — `docs/SCRIPTS.md`):
- `files[]` — полное новое содержимое md-карточек (`create` / `update`). Для `update` взять
  текущую карточку целиком, дополнить; строки с пометкой `(m)` сохранить дословно;
  устаревшее не удалять, а помечать `[obsolete YYYY-MM-DD]`; `style_markers` обновлять
  взвешенно (новая встреча 30 %, история 70 %). Шаблоны карточек —
  `${CLAUDE_PLUGIN_ROOT}/templates/`.
- `records[]` — записи реестров: `append` (новое обязательство/риск/решение/поручение),
  `update` (изменение статуса или полей существующей записи по `id`, с полем
  `change_reason` и источником), `close` (перенос в `closed`/`closed` с историей).
  `done` — только с подтверждением результата. Обновление без подтверждения пользователя
  — не выше `in_progress`.
Для изменений не из встречи (слова пользователя, документ) — использовать служебный id
`YYYY-MM-DD-manual-update-N` как `meeting_id` каталога, создав его через `na.py source create
--provider user_confirmation` с кратким текстом пользователя как источником.

**5. Показать diff.**
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT knowledge diff --meeting <id>
```
Ошибка «пометка (m) потеряна» → исправить proposal. Показать пользователю `knowledge_diff.md`
в структуре: Добавить · Изменить (объект, было, станет, основание) · Противоречия и дубликаты ·
Не вносить пока (чего не хватает, вопрос) · Требуется подтверждение. Спросить: «Применить?»
Можно предложить применить часть — тогда убрать остальное из proposal и показать diff снова.

**6. Применить только после явного «да».**
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT knowledge apply --meeting <id> --confirm
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT refresh-all
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT manifest --meeting <id>
```
Повторный `apply` того же proposal ничего не дублирует. Ошибки `refresh-all` не скрывать и не
объявлять обновление готовым. В режиме проекта — записать изменённые файлы в проект
(`store-adapter.md`, раздел «Запись»).

**7. Закрытия и решения по очереди.** Закрыть обязательство, риск, пункт очереди — только
отдельной командой пользователя:
```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/na.py --root ROOT review record --item <rq-id> --decision "<слова пользователя>" [--status closed|deferred]
```
Закрытие обязательства или риска оформлять как `records[].action: close` в proposal с
`evidence` = подтверждение пользователя или документ. Исходная запись сохраняется в истории.

**8. Показать итог.** Что добавлено, что изменено, какие события записаны в журнал, что
осталось в очереди решений; предложить следующий открытый пункт.

## Стратегические разборы

Выводы стратегического модуля (`conversation-strategy`) не переносятся в карточки людей
как свойства. Только отдельные фактические утверждения с EvidenceRef могут войти в proposal.
Сами разборы хранятся отдельно (`advice/`) по правилам того навыка.

## Чего не делать

- Не писать в `knowledge/` напрямую, минуя proposal → diff → подтверждение.
- Не удалять историю; не перезаписывать `(m)`.
- Не закрывать статусы по умолчанию и не ставить `done` без результата.
- Не объединять сущности по одному имени.
- Не превращать интерпретацию или гипотезу в факт карточки.
